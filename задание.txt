Цель задания: получить практику мониторинга ML-сервиса: сбор метрик в Prometheus и дашборды в Grafana. Задание развивает ваш сервис скоринга фродовых транзакций из предыдущих домашних заданий. Чтение потока из Kafka, выдача скора и переобучение модели остаются. Поверх них появляется наблюдаемость: по дашборду видно, с какой скоростью сервис обрабатывает поток, как распределены скоры и в какой момент скоринг подхватил новую версию модели.
Для выполнения рекомендуется изучить практическую часть занятия 11. Код семинара загружен на GitHub: https://github.com/NikitaMalykhin/mlops_realtime_fraud_detector_monitoring. По нему видно, как поднять Prometheus и Grafana рядом со скорингом, какие метрики отдаёт сервис и как они собираются в дашборды.
Можно опираться на свою кодовую базу с прошлых заданий или на код семинара. Сдаётся ваш публичный репозиторий. Контракт скоринга менять не нужно: сервис по-прежнему читает сообщения с транзакциями и отдаёт скор и флаг фрода. Тяжёлая архитектура модели не требуется, inference выполняется на CPU. Качество модели не оценивается. Метрики должны сниматься с живого потока, а не с одного прогона по статичному файлу.
Требования к реализации
Не пугайтесь: всё, что перечислено ниже, уже сделано в примере с семинара. Имена метрик могут отличаться от семинарских. В README должен быть список ваших метрик и дашбордов, чтобы их можно было найти без устных пояснений.
В docker-compose.yml вместе с уже существующими сервисами скоринга поднимаются Prometheus, Grafana и Node Exporter. Сервисы находятся в одной сети.
Prometheus забирает метрики сервиса скоринга, сервиса записи результатов и Node Exporter. Интервал сбора короткий, чтобы при проверке графики обновлялись сразу. На семинаре интервал — 1 секунда.
Сервис скоринга отдаёт метрики в формате Prometheus по HTTP. Значения обновляются на каждом обработанном сообщении. Минимальный набор:
счётчик обработанных транзакций;
время обработки одной транзакции;
гистограмма скоров;
доля транзакций, помеченных как фрод.
Сервис, который читает топик со скорами и пишет их в PostgreSQL, тоже отдаёт метрики: число записанных скоров, время записи, число транзакций с флагом фрода и гистограмму записанных скоров.
Node Exporter отдаёт системные метрики: загрузку CPU, память, сеть и диск.
Grafana открывается по адресу из README, логин и пароль там же указаны. Источник Prometheus подключается сам, без ручной настройки после запуска. Дашборды лежат в репозитории и появляются при старте. На семинаре это сделано через provisioning.
Дашбордов минимум три.
Обработка транзакций: скорость потока, время обработки, доля фрода, распределение скоров во времени.
Запись результатов: скорость и время записи в базу, число выявленного фрода, распределение записанных скоров.
Системные метрики: CPU, память, сеть, диск.
На дашборде скоринга видна смена версии модели. Сервис увеличивает счётчик с меткой новой версии, когда подхватывает новый файл модели без перезапуска контейнера. Grafana отмечает этот момент на графике. На семинаре отметка держится около 30 секунд и подписана версией модели.
README.md описывает, как поднять проект, где открыть Grafana и Prometheus, какие дашборды смотреть и как убедиться, что метрики растут вместе с потоком, а после прогона переобучения на графике появляется отметка новой версии.
По инструкции из README не должно возникать проблем с поднятием контейнеров и открытием дашбордов.
Что проверяется
Переобучение из прошлого задания заново не оценивается. Нужны работающий скоринг потока и публикация новой модели: иначе на графике нечего отмечать.
docker-compose.yml поднимает стабильно работающие контейнеры скоринга, Prometheus и Grafana.
Сервис читает поток из Kafka и отдаёт скор. Страница метрик растёт, пока идёт поток.
В Grafana открываются три дашборда, и на них есть данные, а не пустые панели.
После публикации новой модели на дашборде скоринга появляется отметка смены версии.
README позволяет повторить запуск и проверку без устных пояснений.
Оценивание работы
Оценка 6-7 баллов
Проект загружен в репозиторий GitHub, и при проверке выполняются все пункты выше.
Набор метрик и дашборды собраны вами. Копия json-дашбордов и конфигурации Prometheus из репозитория семинара на эту оценку не засчитывается. Среди метрик скоринга должна быть хотя бы одна, которой нет в коде семинара. В README напишите, зачем она нужна и на каком графике её смотреть.
Оценка 8-10 баллов
Реализованы дополнительные требования:
В Grafana настроены алерты. Правила лежат в репозитории и появляются после запуска. Минимум два правила на метриках вашего сервиса. Например: доля фрода выше заданного порога и остановка потока или рост времени обработки. Пороги и способ проверить срабатывание описаны в README. Доставка в Telegram или почту не требуется: алерт должен быть виден в разделе Alerting.
К техническим метрикам Prometheus добавлен срез из PostgreSQL. В Grafana подключён источник данных PostgreSQL, и на дашборде есть панель с числом скоров и долей фрода в разрезе версии модели. Так на одном экране видно и то, что процесс жив, и то, какая версия модели что насчитала.
Реализовать в дэшборде Grafana графики с фильтрами по Штатам (us state) и Мерчендайзерам (merch). Пользователь должен иметь возможность выбрать значения для этих колонок и данные на графике должны отфильтроваться. Типы графиков:
плотности распределения скоров
TPS обработки таких транзакций
Добавить barplot со средней долей фродовых транзакций по категории продукта (cat_id) в последних 1000 транзакций.
Добавить как минимум 1 график на свое усмотрение, который мог бы помочь лучше понимать бизнес-процессы в рамках задачи детекции фрода.
